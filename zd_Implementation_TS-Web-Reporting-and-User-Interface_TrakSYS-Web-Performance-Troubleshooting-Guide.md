# TrakSYS Web Performance Troubleshooting Guide

*Source: https://portal.parsec-corp.com/hc/en-us/articles/51823320390419-TrakSYS-Web-Performance-Troubleshooting-Guide*
*Last updated: 2026-05-22T18:11:05Z*

---

### Summary

This article outlines several techniques for troubleshooting performance issues within the TrakSYS Web. These issues may include scenarios where the application loads slowly or fails to load entirely. The troubleshooting methods described are not presented in a specific sequence and are intended to help validate different aspects of the environment and TrakSYS Web configuration. Not every method will apply to every scenario, as applicability depends on the nature of the issue, the specific environment, and application configuration. Some troubleshooting steps may require modifications to TrakSYS Web Settings within the Installation Manager. Because these settings affect the entire web application, a [**TrakSYS Web Application Reload**](https://portal.parsec-corp.com/hc/en-us/articles/360006969353-Reloading-the-TrakSYS-Application) is required for the changes to take effect.

### General

  * **Check if** _**all**_**pages are affected** \- Navigating to different pages under different Sections, Hubs, and Spokes can confirm whether the behavior is isolated to specific pages or if the entire TrakSYS Web application is being affected. This also includes pages under the built-in Sections (Developer, Administration, and Configuration).  

  * **Check what** _**types**_**of pages are affected** \- If not all pages are affected, it is recommended to check Visual Pages, Custom Content Pages, and built-in Content Pages. In many cases, it is possible that only Visual Pages or Custom Content Pages are affected, while built-in Content Pages load without issue. This can usually point to potential issues with efficiency in custom code, part configuration, queries, and more.  

  * **Create a blank Visual Page Definition for testing purposes** \- This test normally involves creating a blank Visual Page Definition with no Parts or custom code. This provides a baseline instance of a page with no additional functionality or content. After creating the page, navigate to it and monitor the page load time to determine whether the issue also occurs on a blank page.  

  * **Enable Page Trace to display loading times** \- When tracing is enabled, the output displays loading times for individual components of the page. This can help identify which portions of the page load process are contributing most to the delay. For Visual Page Definitions, users with the appropriate permissions can enable tracing by selecting the eyeball icon in the bottom menu. Alternatively, tracing can be enabled for any page by adding `trace=1` to the page URL as a query string parameter. It is recommended to review trace output across multiple pages to determine whether elevated load times are consistently occurring within the same areas of the application.  

  * **Access the TrakSYS Web with different browsers** \- Attempting to access the TrakSYS Web with different types of browsers can help determine if client side performance issues due to browser issues. If possible, it is recommended to use Microsoft Edge, Google Chrome and Firefox. If mobile devices are being used for testing purposes, the stock Android Mobile Browser or stock iOS Mobile Browser is recommended. If the performance issues no longer occur on different browsers, it is recommended to clear all cookies and cache from the original browser. If this does not resolve the issue, resetting the browser back to the default manufacturer settings is recommended.  

  * **Access the TrakSYS Web with different devices** \- This can include PC's, laptops, terminals, smartphones, tablets, and more. This helps determine whether the performance issues are isolated to specific devices or if all devices are affected.  

  * **Access the TrakSYS Web directly on the same network as the TrakSYS Server** \- If a client device is using a VPN, proxy, or some other method to access the TrakSYS Web, it is recommended to use a device that is directly connected to the same network as the TrakSYS Application Server for testing purposes. Doing so can help determine whether the VPN or proxy is causing the performance issues.  

  * **Use the browser Developer Tools (F12)** \- Most modern web browsers include built-in Developer Tools that can typically be opened by pressing `F12`. These tools provide features for monitoring individual web request durations, analyzing memory usage, performing performance profiling, and troubleshooting client-side behavior. In addition, the Console tab can be used to identify client-side web errors, JavaScript exceptions, and other browser-related issues. After opening the Developer Tools, it is generally recommended to refresh the page (`F5`) so that the browser can capture the complete page load activity and related diagnostics.   

  * **Check if other parts of the TrakSYS software are also experiencing performance issues** \- This can include Logic Service [**overscans**](https://portal.parsec-corp.com/hc/en-us/articles/115004188434-Logic-Service-Scan-Overview) or [**overwaits**](https://portal.parsec-corp.com/hc/en-us/articles/33344150090387-Overwait-Explanation), Data Management Service Modules that are slow to execute, or don't execute at all, Workflow Processes that don't progress as expected, Historian Tag values that are not recorded as they should, and more. In some cases, slow TrakSYS Web performance may only be a symptom of a larger issue that can affect multiple parts of the TrakSYS software. Normally, the TrakSYS Web is noticed first as this involves heavy interaction with users.   

  * **Access the TrakSYS Web directly using the TrakSYS Application Server (or Web Server)** \- Doing this can eliminate many possible variables and helps determine whether the issue is only experienced by client machines or if the TrakSYS server itself experiences the same issue. For installations that use a dedicated Web Server, the TrakSYS Web should also be accessed directly using that machine as well. If pages load without issue on these servers, but all clients experience issues, this can typically point to possible environment-related issues.  

  * **Check if the issue occurs on multiple environments** \- Evaluating whether the issue occurs across multiple environments (e.g., Production, Development, Testing, and QA) can help determine if the behavior is isolated to a single environment or present across several. If the issue is limited to a specific environment, it is recommended to compare its configuration against an unaffected environment. Particular attention should be given to identifying significant differences in environment-level settings and TrakSYS configuration that may contribute to the observed behavior.  

  * **Check the system resources on the TrakSYS Application Server (or dedicated Web Server)** \- When pages are accessed and the issue is occurring, it is recommended to verify the resource usage of the servers using Windows Task Manager and Performance Monitor. This can help ensure that there are no bottlenecks (e.g., CPU, RAM, Disk Queue Length, etc.) occurring that might be contributing slow loading times.  
  
**NOTE** : If the installation is experiencing issues related to RAM usage or memory management, upgrading to TrakSYS 12 or later may be beneficial. Versions prior to TrakSYS 12 use a 32-bit architecture, which imposes more restrictive memory limitations. Starting with TrakSYS 12, a 64-bit architecture is used, which significantly increases memory limitations in some scenarios.  

  * **Ensure that database table indexes are de-fragmented** \- If the performance issues are gradual and get noticeably worse over time, this is typically a sign that table indexes are getting fragmented. This can have adverse effects on pages that have a large number of queries or pages that query data for larger Date/Time ranges. The general recommendations for defragmenting table indexes can be found [**here**](https://portal.parsec-corp.com/hc/en-us/articles/228902187-Defragmenting-Database-Table-Indexes).  

  * **Identify any patterns in which the performance issues are occur** \- If the performance issues intermittently occur, it can be helpful to identify any patterns that may arise. For example, the issues may only occur at certain times, certain days of the week, when a specific number of users access the TrakSYS Web, when specific scripts or queries are executed, etc. While some patterns may only be symptoms of the root cause, identifying patterns can help narrow the overall scope of possible root causes.  

  * **Verify network speeds, throughput, and performance** \- It is recommended to use network monitoring tools (where available) to assess network performance. This is particularly important in distributed deployments involving multiple servers. Key indicators to review include failed connection attempts, packet loss, intermittent connectivity issues, and any other network-level anomalies that may impact performance. In general, it is recommended to view the [**TrakSYS Bandwidth and Latency Requirements**](https://portal.parsec-corp.com/hc/en-us/articles/1500002559941-TrakSYS-Bandwidth-and-Latency-Requirements) to ensure that the application performs adequately even during peak load times.  

  * **Check the log files** \- This can include the [**TrakSYS log**](https://portal.parsec-corp.com/hc/en-us/articles/115003466434-Exporting-the-TrakSYS-Log), the Event Viewer log in Windows, and any network monitoring software logs. If messages are available, this may help provide additional insight into why performance issues are occurring. The different types of TrakSYS logging can be found [**here**](https://portal.parsec-corp.com/hc/en-us/articles/6827052105235-Types-of-Logging-in-TrakSYS).  

  * **Temporarily disable Web Load Balancing** **and/or Network Load Balancing** \- If either of these methods are used to help distribute web traffic, it is recommended to temporarily disable these to see if the issues still occur. If the performance issues no longer occur and Web Load Balancing is being used, it is recommended to route all traffic to the primary Web Server first. If no issues are detected, the traffic can then be routed through the second Web Server. This process can be repeated for each Web Server involved until the root cause is identified. If individual web servers perform as expected in isolation but issues occur only when load balancing is enabled, this may indicate a configuration issue within the load balancing setup.  

  * **Ensure that the TrakSYS Web Settings have been optimized** \- If the performance issues are experienced on the Production Server, it is recommended to optimize the TrakSYS Web Settings as mentioned [**here**](https://portal.parsec-corp.com/hc/en-us/articles/236362487-Optimizing-TrakSYS-Web-Settings). These settings disable extra logging and debugging that is only needed for web development and should only be enabled on the Development Server. Note that if any changes within the article are saved, it is recommended to [**Reload the TrakSYS Application**](https://portal.parsec-corp.com/hc/en-us/articles/360006969353-Reloading-the-TrakSYS-Application) to ensure that are applied to the Web application.
