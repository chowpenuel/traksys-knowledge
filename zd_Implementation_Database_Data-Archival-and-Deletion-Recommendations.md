# Data Archival and Deletion Recommendations

*Source: https://portal.parsec-corp.com/hc/en-us/articles/50695271477139-Data-Archival-and-Deletion-Recommendations*
*Last updated: 2026-06-03T14:43:51Z*

### Summary

Regular database maintenance is a critical component when managing TrakSYS installations. Over time, production databases can accumulate large volumes of historical records. This can include entities such as Jobs, Events, Tasks, Batches, Production Counts, Audit Records, and more. The rate and speed in which these records accumulate greatly depends on the configuration and volume of usage. If neglected, this data accumulation will eventually consume excessive disk space, degrade query performance, increase backup windows, cause TrakSYS upgrades to take longer, and more. 

To address these issues, it is recommended to archive older data that is still needed, but may not be referenced (such as keeping audit records that are required by government agencies). One this is done, the primary TrakSYS database can be purged of this information. This article contains the recommendations for archiving old database records and clearing out the original records from the TrakSYS database. Since there are multiple ways this can be accomplished, it is recommended to confirm with the Site's internal IT department to ensure that these methods follow internal and regulatory (if any) protocols. 

### Data Evaluation

Before beginning, it is recommended to view how many rows of data are in each table within the TrakSYS database for Data Entities. All tables that are considered Data Entities can be found [**here**](https://portal.parsec-corp.com/hc/en-us/articles/115002120954-What-Tables-and-Fields-Are-Excluded-from-Database-Transfer). There are multiple ways to do this, but the methods below can be used to quickly generate this information. If only a simple list of tables and row counts are needed, it is possible to return this information using the following query:
    
    
    SELECT
        t.TABLE_NAME AS TableName,
        p.rows AS [RowCount]
    FROM
        INFORMATION_SCHEMA.TABLES t
        INNER JOIN sys.tables st ON st.name   = t.TABLE_NAME
        INNER JOIN sys.partitions p ON  p.object_id = st.object_id
        AND p.index_id  IN (0, 1)  -- 0 = heap, 1 = clustered index
    WHERE
        t.TABLE_TYPE = 'BASE TABLE'
    ORDER BY
        p.rows DESC,
        t.TABLE_SCHEMA,
        t.TABLE_NAME;
    

If more information is needed or an official report needs to be generated displaying this information, it is possible to use the built-in reporting functionality within SQL Server Management Studio. The report can be generated by right clicking the TrakSYS database and selecting **Reports | Standard Reports | Disk Usage By Table**.

![](https://portal.parsec-corp.com/hc/article_attachments/51861150969491)

Once the report has been generated, the Sort button can be clicked to display tables with the highest number of records.

This will allow users to see which Data Entities have the most number of records and determine which tables should be purged.

### Data Archival

When archiving older production data, it is recommended to take a backup of the current TrakSYS database and restore it as a separate database with a different name. The recommended procedure for backing up and restoring the TrakSYS database can be found [**here**](https://portal.parsec-corp.com/hc/en-us/articles/16353780129683-Backup-and-Restore-a-SQL-Server-Database). If the Site is using the [**TrakSYS Historian**](https://portal.parsec-corp.com/hc/en-us/articles/360005775213-Using-the-TrakSYS-Historian) feature, this same process is also recommended for the Historian Database.

**NOTE** : If there is no production data that needs to be archived and the data can simply be deleted, proceed to the "Production Data Deletion" section below.

This restored copy serves as a point-in-time archival database which contains a snapshot of all historical data as it existed prior to the cleanup. This approach gives the Site a reliable reference for audits, compliance reviews, or historical reporting without impacting the performance of the live TrakSYS production database. 

While this method can be used to preserve data, there are some caveats and limitations that should be considered:

  * Database Licensing



The archived database will not be licensed, so users will not be able to access the TrakSYS Web. Additionally the TrakSYS Services to will not be allowed to run to actively collect data. Therefore, the data is primarily meant to be queried through Management Studio.

  * Reporting on data in the Archived Database



It is possible to configure reports to query data from this database. However, this means the reports will be configured to connect to an external database. Therefore, a different connection string or a duplicate copy of each report will need to be created to look at the older data. This will likely require additional development time and can complicate application maintainability.

  * Archive Database Maintenance



In a vast majority of cases, the TrakSYS version of the archived database will likely not be maintained. As the primary TrakSYS database is upgraded, this will not upgrade the archived database. This also means that any schema changes that are included in newer updates will not be applied to the archived database. While the archived database can technically be upgraded, the functionality and troubleshooting will be very limited as no license will be present. For example, if the upgrade on the archived database fails and the fix requires the user to access the TrakSYS web or interact with any of the TrakSYS Services, this will not be possible. 

### Production Data Deletion

Before removing data from the TrakSYS database, it is **strongly** recommended to take a [**database backup**](https://portal.parsec-corp.com/hc/en-us/articles/16353780129683-Backup-and-Restore-a-SQL-Server-Database). Doing so provides a contingency option in case required data is accidentally deleted or if the application experiences major issues after data is removed. Additionally, this process should only be performed during planned downtime while all TrakSYS services are stopped. It is recommended to **never** perform these operations while any of the TrakSYS services are running.

#### Delete Query Recommendations

When removing production data, it is recommended to delete data in chunks using a raw SQL statement. When a DELETE statement is used, the removal for individual records is stored within the SQL Server Transaction Log. If a single DELETE statement is used for all production data, this can cause the log file to rapidly consume available disk space on the environment. For large data sets, this can exhaust available disk space and potentially cause the environment to become unstable or fail. Deleting records in smaller batches helps control Transaction Log growth and reduces the risk of consuming all available disk space.

Depending on the number of records being removed, this process may take a significant amount of time to complete. Increasing the number of records deleted per batch may improve performance. For example, deleting 100,000 records per batch instead of 10,000 may significantly reduce the overall execution time. However, the appropriate batch size depends on the server hardware, database configuration, Transaction Log capacity, and available disk space. Batch sizes should be adjusted based on the specific environment.

To assist with this process, a .sql file has been provided to use as a starting point for the delete query. **Do not execute the query as-is**. Further modifications (such as specifying a valid Date/Time range, placing the statements in a transaction, executing the statements in a loop, and more) are **strongly recommended**. The file includes instructions and provides a list of cascading tables that will be affected by each DELETE statement.
