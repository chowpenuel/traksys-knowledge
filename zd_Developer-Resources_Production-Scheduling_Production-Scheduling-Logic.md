# Production Scheduling Logic

Applies To | TrakSYS 11 | TrakSYS 12

### Summary

This article contains a high level overview of how Production Scheduling engine functions. This is triggered by calling the ProdSched ApiService, using the Schedule method. The logic is complex and involves a number of different loops, many of which are nested. To try and simplify this, the logic has been broken into many segments. The expected reading pattern is to start from the first section listed (Initialization), to read the full section, and then to follow the logic into the lower layers as needed.

### Article Formatting

There are formatting patterns within this article that are unique to this article due to the complexity of the topic being presented. These many not follow the pattern of other articles within the support site, so it is highly recommended to review these before reading the rest of the content.

Within a section, there will be sub-sections. These are denoted as `code tags`. Each Code Tag has it's own full section that further describes the logic. This pattern will repeat for many layers.

For example, in the Initialization Section, there is a Code Tag for `Internal Scheduling Method`. This means that there is a Internal Scheduling Method Section. Within the Internal Scheduling Method, there is a `Scheduling Service` Code Tag. Therefore, there is a Scheduling Service Section. 

Within a Section, there may also be specific colors associated with some of the lines. These are meant to identify something special about the line. 

Lines in the darker blue color are Plugin Hooks. This are the defined locations where a Production Scheduling Plugin can be used to add additional Logic to the Schedule Method logic. For a more specific article on only the execution of the Plugin Hooks, see [**this article**](https://portal.parsec-corp.com/hc/en-us/articles/360046038413).

Lines in the red color are only relevant to the Batching variation of the Production Scheduling. This logic will **not** run when scheduling a Discrete Production Scheduling Set. 

### Initialization:

Verify pre-requisites before scheduling.

  * A PsSettings object is required (but is not validated until later).
  * A valid Production Scheduling License is required.



Long Running Activity content is initialized.

`Internal Scheduling Method` starts.

  * This is encapsulated in a Try-Catch, which will output the last exception encountered.



Return the PsStage Generated by the Internal Scheduling Method.

### Internal Scheduling Method:

Validate pre-requisites before scheduling

  * The PsSettings Object requires a PsSetID
  * The number of Scheduling Systems is verified against the License.
  * The PsSet is loaded.



Start the `Scheduling Service`

  * There are two variants of this Scheduling Service, one for Batch and one for Discrete.



Return the PsStage generated by the Scheduling Service.

### Scheduling Service:

  * This is the major process. It will include various loops that are defined under their own headers for better readability.



Prepare general variables

  * Sets the Plugin, Settings, CurrentTime (as Now), and TimeZone information.



Plugin.Init

  * Provides access to the Now and Settings. Now can be updated.



Set the MinStart and MaxEnd

  * MinStart is set to 10 minutes after Now. MaxEnd is calculated using the Setting’s Schedule Duration Dates and the Now.



Plugin.CalculateScheduleRange

  * Provides access to a DateTimeRange object that can be used to override MinStart and MaxEnd.



Create the PsStage using the Settings information and Now

  * The stage is inserted at this time and can be seen in the Database in tPsStage. It will not have any child records at this time.



Create the Updater object for Long Running Activities.

Plugin.PostCreatePsStage

  * Provides access to the PsStage and Updater objects. By default, a plugin will synchronize the Updater object with the one in the Plugin.



`Load Job List`

  * Returns a sorted Job List.



Get a list of all Systems using the PsSetID.

`Load System List`

  * Returns a list of validated Systems.



`Load Shift Information For Systems`

  * Updates the System Information objects for the Unavailable Times lists.



Prepare the Job Lists

  * Creates the JobsToSchedule, JobsUnscheduled, and JobsAssigned lists.
  * Populates the JobsToSchedule list with the sorted Job List. This also includes the sortIndex scores.



Plugin.PreScheduleJobs

  * Provides access to the General Context object, which includes all of the Job Lists.



`Main Scheduling Loop`

  * Starts the primary scheduling logic that iterates until all Jobs are Scheduled or are unable to be Scheduled.



Plugin.PostScheduleJobs

  * Provides access to the complete list of JobsAssigned and JobsUnscheduled before processing for save.



Prepare for Save

  * Creates Unit of Work.
  * Updates PsStage to include diagnostic details.



Plugin.PreSavePsStageJobs

  * Provides access to the UnitOfWork before Jobs are saved.



Create PsStageJob records

  * Creates a record for each Job in the JobsAssigned List.
  * Creates a record for each Job in the JobsUnscheduled List with default values.



Plugin.PostSavePsStageJobs

  * Provides access to the UnitOfWork with the PsStageJob records. This occurs before they are saved.



Execute Unit of Work

  * This is the final Save of the process.



Plugin.PostUowExecute

  * This is the final plugin hook before returning the final PsStage record.



Return the PsStage.

### Load Job List:

Get a list of all valid Jobs using the PsSetID.

  * This includes any jobs for the PsSet that have not executed. It uses the GetList.OfPsRequestedJobsForPsSetID method for this process.



`JobList Loop`

  * Loop through each Job, returning a list of Jobs to be Scheduled.



Jobs are sorted based on the Sort Priorities in the PsSchedule Object.

  * This defaults to the PsRequestedDateTime, PsPromisedDateTime, and PsRequestedPriority in that order.



Plugin.ResortJobList

  * Provides access to the sorted Job List. This list can be resorted and returned for use by the rest of the scheduling logic.



Return the sorted Job List. The List Order is saved as JobIndex values for later Scoring Criteria.

### JobList Loop:

Verify each Job

  * Job Name cannot be empty and must be unique.



Plugin.ShouldScheduleJob

  * Provides access to the Job object and expects a Boolean result. If a value of False is returned, the job will **NOT** be scheduled.



Add job to a list to be scheduled. Return the Job List when the loop is completed.

### Load System List:

Get a list of all valid Systems using the PsSetID.

  * This uses the GetList.ForPsSetID method.



`SystemList Loop`

  * Loop through each System, returning a list of Systems with SystemInfo objects.



### SystemList Loop:

Validate the System.

  * Ignore Systems that are Disabled, the wrong Type, are Template Parents, are Sub Systems (only the Parent Systems are used), or are in a disabled Area.



Set the default minimum starting time for the System to Now.

Attempt to load the Previous Job Information.

  * Loads the most recent Job System Actual for the System ID. Uses the Start and End time for the Job, as well as the Product (and Recipe) ID.
  * Uses the Job information to create a JobEstimateInfo object.



If the Previous Job is not NULL, use it to set a new Min Start.

  * If the job is active, use the Kpi.LoadJob<Type>EstimateData and Kpi.CalculateEstimatedJob<Type>End methods to estimate the end of the Job. Adds the Job’s Post Padding/Changeover/Gap seconds to get a new EndDateTime.
  * If the job is not active, check the EndDateTime.
  * In either scenario, if the EndDateTime is later than the current MinStart for the System, it is updated to the new EndDateTime.



Plugin.ShouldScheduleForSystem

  * Gives access to the current SystemInfo, the current MinStart, and the PreviousJobInfo.
  * If the method returns false, the System will not be scheduled.



Plugin.CalculateMinStartDateTimeOfrSystem

  * Gives access to the current SystemInfo, the current MinStart, and the PreviousJobInfo.
  * Can be used to return a new MinStart for the System.



Add the SystemInfo to a list. Return the list when the loop is completed.

### Load Shift Information For Systems:

Loop through each System - load the Unscheduled Time and convert it to a List of Unavailable Times.

  * This process uses the ProdSched.CreateUnscheduledTimeForScheduleID call.



Plugin.UpdateUnavailableTimesForSystem

  * Provides access to the System Context and the new Unavailable Times List.



### Main Scheduling Loop:

Start tracking time for a Timeout Duration.

  * The duration for a timeout is based only on the time taken for the main scheduling loop. All loading and post-processing is excluded and occurs regardless.



Plugin.PreScheduleInfoForJobSystems

  * Provides access to all of the Job Lists, which is updated every loop.



`Build Score Info`

  * Loops through every JobInfo/SystemInfo combination to create a ScoreInfo.



`Evaluate Score Info`

  * Sets up scaling for each Score and Evaluates to determine the Best Job.



Assign Best Job

  * Adds the Best Job to the JobsAssigned List and removes it from the JobsToAssignList.
  * Assigns the JobInfo to the Best Job object in context until the end of the Loop.



Update System Info

  * Adds a new UnavailableTime to the BestJob’s System.
  * Assigns the BestJob info to the System’s PreviousJobInfo for use in future loops.



Plugin.PostScheduleInfoForJobSystems

  * Gives access to the General Context, which now includes the Best Job, Updated Lists, and Updated SystemInfo.



Check for Timeout

  * If the timeout is reached, remaining Jobs are assigned to the JobsUnscheduled with a Message and Activity Log.



Plugin.PostScheduleJobs

  * Provides access to the final version of the Job Lists before they are processed for saving.



### Build Score Info

Load Product

  * Attempts to load a Product using the PsRequestedfProductCode from the Job and the ProductSetID from the System.



Plugin.LoadProduct

  * Provides access to the Product that was loaded along with the ability to return an alternate product if desired.



Load Changeover

  * Attempts to load a Changeover Type using the System’s ProductSetID, the Previous Job’s Product (this can be null), and the current Product.
  * This uses the Product’s ProductCoFamilyID’s and the “Data.DbProductCoType.GetList.ForProductCoTypeSetIDAndCoFamilies” method, returning the first result from the list.



[Batch Only] Load Recipe

  * Attempts to load a Recipe using the current Product and the System’s ID. This will ignore Disabled Recipes, and Recipes not in an Active Version State. It can use Recipes from a Parent Template System but will prioritize Recipes on the specific System.



[Batch Only] Plugin.CalculateRecipeToUse

  * Provides access to the Recipe that was loaded with the ability to return an alternate recipe if desired.



[Batch Only] Validate Recipe

  * If a new value is provided, it will be validated before the process continues. This can occur if the System is Invalid, the Recipe is not configured for the assigned System, or the Product and Recipe do not have matching Versions.



Calculate Job Duration

  * The JobDuration information is set using the Job, Product, Recipe, and Changeover information from the previous steps.



Plugin.UpdateJobDuration

  * Provides access to the populated Duration information, which can be updated before the Job is scheduled.



`Try Schedule Job For System`

### Try Schedule Job For System

Verify Job Duration

  * If the Job’s Duration is zero, it will be rejected with an error message.



Assign Job’s Next Available Time

  * The initial Next Available Time is set to the be System’s Minimum Start Time or the Job’s PsRequestedDateTime (whichever is later). This value will be utilized for the rest of this method and will be updated until a viable time is found or until it is rejected.



Plugin.ShouldScheduleJobOnSystem

  * Provides access to the current Job and System information. Returning False will prevent this Job from being scheduled on this System for this loop.



Plugin.CalculateMinStartDateTimeForJobOnSystem

  * Provides access to the current Job and System information. The Next Available Time is accessible and can be updated before the algorithm attempts to find a suitable spot for the Job. If a new Next Available Time is provided, it must be equal to or later than the provided one.



`Find Spot For Job`

  * Determine when the Job can run on the current System with the given Unavailable Times and Planned Duration information.



Plugin.CalculateNextPlannedStartDateTime

  * Provides access to the Score Info for the Job and System, which includes the scheduled Time and the Duration information. This can be updated before reaching the Scoring stage.



### Find Spot For Job

This method and its sub methods will be utilizing three main timestamps: Total End, Gap End, and Calculated End. Each of the timestamps compares the current Next Available Time and adds a duration to determine an End Time. As the Next Available Time updates, these are recalculated.

  * The **Total End** adds the Job’s Total Duration.
  * **Gap End** adds the Total Duration excluding ChangeoverPostSeconds.
  * **Calculated End** adds the Total Duration except for ChangeoverPostSeconds and GapPostSeconds.



The loop will continue until data is returned. Throughout the description, there will be two key terms: “Continue” and “Return”. 

Continue means the current Next Available Time is not valid. If the Extend Over Unscheduled property is true, this will lead into the sub-section to Evaluate Over Multiple Unavailable Times. Otherwise, this will reset the loop. When this happens, the Next Available Time is updated as well.

Return means that the loop will end. At this point, a value has been determined and will be passed up to the previous method. A NULL return means it could not be scheduled. Any other value indicates that the loop's Next Available Time was valid.

Check Total End against Schedule Max End

  * If the Total End is beyond the Schedule Max End, return NULL. It cannot be scheduled in the remaining time.



Check for Unavailable Times

  * If none are found, the job can be scheduled. Return the current Next Available Time.



`Evaluate Over Current Unavailable Time`

  * This will attempt to find a slot between Unavailable Times. If Extend Jobs Over Unscheduled Time is enabled, there is a sub-method to process a more detailed evaluation.



### Evaluate Over Current Unavailable Time

Calculate End Times

  * If the Next Available Time is before the Unavailable Time’s End, this is not relevant. It will continue to the next Unavailable Time.
  * If the Next Available Time is between the Unavailable Time’s Start and End, it is inside the Unavailable Time. It will continue to the next Unavailable Time.



Check if Job can complete before Unavailable Time

  * If the Total End is before the Unavailable Time’s Start, it can be scheduled. Then, return the current Next Available Time.



Check if Job Gap can extend into Unavailable Time

  * If the Unavailable Time is a Job, it cannot extend. Continue.
  * If the Calculated End is after the Unavailable Time’s Start, or if the Job has any changeover time, it cannot extend. Continue.
  * Otherwise, there is only Gap time and it can fit in the Unavailable Time, it **can** extend. Return the current Next Available Time.



If a continue was reached and Extend Over Unscheduled is enabled, the logic will continue into the `Evaluate Over Multiple Unavailable Times` method. Otherwise, a continue will restart the loop, using a new Next Available Time.

Check Last Time against Schedule Max End

  * If all Unavailable Times were evaluated and no suitable time was returned, check one more time using the last Unavailable Time’s End as the Next Available Time.
  * If the Total End is beyond the Schedule’s Max End, it cannot be scheduled. Return NULL. Otherwise, return the Next Available Time.



At this point, either a value has been returned and a Score Info object has been created, or the Job could not be scheduled and will return NULL. This will feed back up the logic chain to the Build Score Info method, where it will return the appropriate Score Info object for the Evaluate Score Info step.

### Evaluate Over Multiple Unavailable Times

This method uses the same Total, Gap, and Calculated Ends, but tracks ExtendedSeconds. This value gets increased each time a new Unavailable Time is processed and is returned as the “UnscheduledSeconds” property of the ScoreInfo.PlannedDuration object that is returned. The ExtendSeconds is added to the calculation of each End value at the start of the loop.

The logic of this method is identical to the Evaluate Over Current Unavailable Times with two exceptions

  * Each time an Unavailable Time is checked and is insufficient, the duration of the Unavailable Time is added to the ExtendSeconds. This will bump each of the calculated End values into the future.
  * If an Unavailable Time is a Job, it will immediately fail and return Null.



Otherwise, it follows the same steps.

  * Check to see if it can be scheduled immediately.
  * Check to see if it can be scheduled with only some PostGap falling into the Unavailable Time.
  * If all Unavailable Times have been checked, verify whether it can be finished at the end of the last Unavailable Time before the Schedule Max End.



At any time it finds it can be scheduled, it will return the appropriate Next Available Time (which will feed back up the logic chain to the Build Score Info method) where it will return the appropriate Score Info object for the Evaluate Score Info step. This is the last major step before the Evaluate Score Info logic.

### Evaluate Score Info

Verify the Score Info objects

  * If no Score Info Objects are detected, this will end the scheduling process.
  * Plugin.PostScheduleInfoCompleteWithUnscheduledJobs only executes if no Score Info Objects are detected. It provides access to the list of Unscheduled Jobs and provides a clear place to address schedules that fail to schedule completely.



Plugin.InitScores

  * Provides access to the ScoreInfo object List, which can be evaluated and modified before the Score Ranges are calculated.



Calculate Score Ranges

  * Iterates through each ScoreInfo object to determine the Best and Worst value for each Scheduling Criteria.



Evaluate each Score Info

  * Loops through each Score Info for each Criteria to determine how it scored. See **Detailed Scoring Description** for more information.



Plugin.UpdateScores

  * Provides access to the ScoreInfo object List, which contains the evaluated score values. These can be updated and adjusted before the “Best Job” is selected.



Plugin.CalculateLineAffinityScore

  * Provides access to the Score Info Object and allows for the calculation of a Custom Score. This is developer-user and does not have any standard functionality.



Plugin.CalculateCustomScore

  * Provides access to the Score Info Object and allows for the calculation of three Custom Score. This is developer-user and does not have any standard functionality. This method will execute three times. Each time, the ScoreContext.ScoreType value will be updated to identify which iteration it is on. It will return 1, 2, then 3 to signify which iteration is being processed. It is expected that a developer will use this to avoid unintended, repeated execution of a score.



Calculate and return Total Score

  * The aggregate of all scores (custom and standard) is calculated and the final ScoreInfo object is ready for evaluation of the “Best Job” in the next step of the algorithm.



### Detailed Scoring Description

Each Scheduling Criteria is one of three types:

  * Earliest Timestamp Wins (“Earliest”)
  * Lowest Value Wins (“Lowest”)
  * Biggest Value Wins (“Biggest”)



Score is done in two main phases:

Prepare Scoring Criteria:

  * Determine the Scoring Range
  * Determine the Worst Value



Evaluate each Score Info:

  * Determine the Score's Difference from the Worst Value
  * Compare the Difference with the Score Range, then scale it with the Score Weight (provided by the PsSettings) to obtain a Criteria Score.



The Scoring Range is done by taking all of the Score Info objects and finding the Best and Worst values among them. For example, the ChangeoverDurationScore will look at the ChangeoverSeconds of all Score Info objects and retrieves the largest and the smallest values. The difference between these values is the Scoring Range.

The Worst Value is based on the Scoring Type. The names are self-explanatory. For example, ChangeoverDurationScore is a “Lowest” scoring type which means the Best Value is the lowest amount of Changeover, and the Worst Value is the highest amount of Changeover. That means the ScoreInfo with the Lowest ChangeoverSeconds will receive the maximum Criteria Score.

When evaluating a Score Info, the Criteria Score is scaled using three values:

  * Score Range
  * Difference
  * Score Weight



The Difference is calculated using the Score Info’s Value for the Criteria and comparing it with the Worst Value for the criteria. This difference is the divided by the Scoring Range to get a percentage value. This percentage is the multiplied by the Score Weight to get the final Criteria Score.

#### Example 1 – A Biggest Value Wins:

A schedule has a RequestedPriorityScore of 100. In this loop, the highest RequestedPriority is 50, and the lowest is 0. The Score Range for the criteria would be (50 – 0), which is 50. Since this is a “Biggest” Criteria Type, the Worst Value will be 0.

In this example, a Score Info object is being evaluated. It has a RequestedPriority of 10. The Difference would be (10 - 0), which is 10. Comparing this to the ScoringRange (50), the percentage is calculated (10 / 50) which is 20%. This Score Info is 20% of the way from the worst value (0) to the best value (50). This is then used to scale the Score Weight (100) by multiplying the two. The final Criteria Score is (100 * 20%), which is 20.

#### Example 2 – A Lowest Value Wins:

A schedule has a ChangeoverDurationScore of 150. In this loop, the highest ChangeoverSeconds is 1800 and the lowest is 600. The Scoring Range for the criteria would be (1800-600), which is 1200. Since this is a “Lowest” Criteria Type, the Worst Value will be 1800.

In this example, a Score Info object is being evaluated. It has a ChangeoverSeconds of 1500. The Difference would be (1800-1500), which is 300. Comparing this to the ScoringRange (1200) we get the percentage of (300/1200), which is 25%. This Score Info is 25% of the way from the worst value (1800) to the best value (600). This is then used to scale the Score Weight (150) by multiplying the two. The final Criteria Score is (150 * 25%), which is 37.5.

Below are each of the Scoring Criteria and their Criteria Types:

  * PlannedStartDateTime: Earliest
  * RequestedDateTime: Earliest
  * PromisedDateTime: Earliest
  * JobSortPriority: Lowest
  * SystemPriority: Lowest
  * UnitDuration: Biggest
  * PaddingDuration: Lowest
  * GapDuration: Lowest
  * ChangeoverDuration: Lowest
  * RequestedPriority: Biggest



Custom Scores and Line Affinity Scores are **NOT** subject to this scoring pattern. They return a double value, which is the raw score. This score will be added directly to the score total and any scaling desired should be included in the Custom Scoring logic written in the plugin. If you want to use a similar pattern to the standard Scoring logic, you can do so using the Plugin.InitScores method, and the appropriate Custom Score method. An example of creating a Custom Score can be found [**here**](https://portal.parsec-corp.com/hc/en-us/articles/5508823062547).
